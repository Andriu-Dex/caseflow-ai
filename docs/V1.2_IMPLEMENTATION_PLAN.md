# Plan de implementación — CASEFlow AI v2

> Documento de planificación para que un agente (u otro desarrollador) implemente la v2 completa en una sola pasada sobre una sola rama. No es código ni sustituye `AGENTS.md`/`docs/CASEFLOW_AI_SPEC.md` — donde este plan y esos documentos difieran, prevalecen ellos.

---

## 0. Alcance y frontera dura

**Rama de trabajo:** `feat/v2-foundation`, creada desde `main` (que al momento de escribir este plan contiene exactamente el mismo estado funcional que `develop` — ver `docs/PRIMER_PARCIAL_FINAL_EVIDENCE.md` §2).

**Esta v2 incluye, en este orden de dependencia técnica:**

1. Identity / Workspace / Project (autenticación + RBAC)
2. Knowledge Base / RAG
3. Impact Analysis
4. Consistency Engine
5. Baselines

**Esta v2 EXPLÍCITAMENTE NO incluye** (fuera de alcance, no tocar):

- Construction/Code Generation, GenerationPlan, ImplementationPlan, Sandbox, generación de proyectos ejecutables (AGENTS.md §8, §11, §63).
- Living Documentation, Collaboration/Notifications (quedan para v3).
- Cambios visuales/UX no relacionados con estas 5 features.
- Cambios a la infraestructura de despliegue (eso ya está cubierto por `docs/DEPLOYMENT_FREE_TIER.md` si se creó).

**Regla de ejecución para el agente que implemente esto:** aunque todo vaya en una sola rama, **no** es una sola sesión de generación sin control (AGENTS.md §11 prohíbe el one-shot para Construction; aplicamos el mismo espíritu aquí por prudencia). Implementar **increment por increment, en el orden dado**, con su propio commit (o serie de commits) al final de cada increment, corriendo la batería completa de verificación (§7 de este documento) antes de pasar al siguiente. Si algo de un incremento posterior obliga a tocar un incremento anterior, está permitido, pero debe documentarse en el mensaje de commit.

## 1. Incremento 1 — Identity / Workspace / Project (Auth + RBAC)

### 1.1 Motivación

Hoy no existe ningún modelo `User`/`Session` en el schema (`grep` confirmó cero coincidencias). Cualquiera con la URL de la API puede operar cualquier `Workspace`/`Project`. Es la base de todo lo demás: sin usuarios reales, "colaboración" y "revisión humana" son conceptualmente incompletos.

### 1.2 Modelo de datos (Prisma, aditivo — nunca `db push`, usar `prisma migrate dev`)

Nuevos modelos:

- `User` — `id`, `email` (único), `passwordHash` (Argon2id, AGENTS.md §34), `displayName`, `createdAt`, `archivedAt`.
- `Session` — `id`, `userId`, `refreshTokenHash`, `expiresAt`, `createdAt`, `revokedAt`. Los access tokens son de corta vida (JWT firmado, no persistido); los refresh tokens rotan y se persisten hasheados, nunca en texto plano (AGENTS.md §34).
- `WorkspaceMembership` — `id`, `workspaceId`, `userId`, `role` (enum `WorkspaceRole`: `OWNER`, `ADMIN`, `MEMBER`), `createdAt`. Único por `(workspaceId, userId)`.
- `ProjectMembership` — `id`, `projectId`, `userId`, `role` (enum `ProjectRole`: `OWNER`, `EDITOR`, `REVIEWER`, `VIEWER`), `createdAt`. Único por `(projectId, userId)`.

**No** se agrega un modelo `Role` genérico configurable — los roles son un enum fijo (YAGNI: AGENTS.md §21/§51 desalientan flexibilidad especulativa; "custom roles" está explícitamente fuera de alcance de V1/V2 según AGENTS.md §8).

### 1.3 Contratos (`packages/contracts/src/identity/`)

Nuevo archivo `identity.contract.ts` con:
- `registerRequestSchema` (email, password, displayName).
- `loginRequestSchema` (email, password).
- `authResponseSchema` (accessToken, user: {id, email, displayName}).
- `WORKSPACE_ROLES`, `PROJECT_ROLES` como arrays `as const` (mismo patrón que `ARTIFACT_ORIGINS` en `artifact.contract.ts`).
- `inviteMemberRequestSchema` (email, role).

### 1.4 Backend

Nuevo módulo `apps/api/src/identity/` con:
- `AuthController` (`/auth/register`, `/auth/login`, `/auth/refresh`, `/auth/logout`) — rutas públicas, únicas sin guard.
- `AuthService` — hash con `argon2` (agregar como dependencia aprobada; verificar que no exista ya una librería equivalente antes de añadirla, AGENTS.md §51), emisión de JWT de acceso (corta vida, p. ej. 15 min) + refresh token rotativo en cookie `httpOnly`/`secure` (nunca en `localStorage`, AGENTS.md §34).
- `AuthGuard` (NestJS `CanActivate`) — global, aplicado a todos los controladores existentes salvo `/auth/*` y `/health/*`.
- `WorkspaceMembershipGuard` / `ProjectMembershipGuard` — verifican pertenencia real, nunca solo el UUID en la URL (AGENTS.md §33.1, ya es una regla explícita del proyecto).
- Cambios necesarios en **todos** los controladores existentes (15 controladores, ver auditoría §18): decorar con el guard correspondiente y resolver el usuario autenticado en vez de confiar ciegamente en `projectId` de la ruta.

**Punto crítico de migración de datos:** los proyectos/artefactos que ya existen en la base de datos (incluyendo "Préstamo de Equipos Deportivos") no tienen dueño. La migración debe:
1. Crear un usuario "seed" (o pedir al primer usuario que se registre) y asignarlo como `OWNER` de los workspaces existentes vía un script de backfill (`scripts/backfill-workspace-memberships.mjs`), **no** una migración SQL destructiva.
2. Nunca borrar ni sobrescribir datos históricos existentes (AGENTS.md §31.3).

### 1.5 Frontend

- Páginas nuevas: `/login`, `/register`.
- `ActiveProjectProvider` (ya existe) debe extenderse para redirigir a `/login` si no hay sesión válida.
- `apps/web/lib/api.ts`: el `fetch` compartido debe incluir credenciales (`credentials: 'include'`) para la cookie de refresh, y manejar 401 con logout automático + redirect.
- Selector de miembros por proyecto/workspace (invitar por email, cambiar rol) — página nueva o sección dentro de una futura "Configuración de proyecto".

### 1.6 Pruebas mínimas requeridas

- Unit: `AuthService` (hash/verify, emisión/rotación de tokens).
- Integration: registro→login→acceso a un recurso protegido→refresh→logout; **aislamiento cross-workspace** (un usuario sin membership no puede leer/escribir nada de otro workspace — caso P0 explícito de AGENTS.md §62).
- E2E (Playwright): un tercer escenario nuevo, "Escenario C — Auth", que cubra login real por navegador.

### 1.7 Definición de terminado

Ningún endpoint existente queda accesible sin sesión válida y membership verificada, excepto `/health/*` y `/auth/*`. Todas las pruebas de integración existentes deben actualizarse para autenticarse primero (impacto transversal grande — dimensionar tiempo en consecuencia).

## 2. Incremento 2 — Knowledge Base / RAG

### 2.1 Motivación

`pgvector` ya está instalado (extensión habilitada en la migración de Foundation) pero sin ninguna columna vectorial ni uso funcional (confirmado: cero coincidencias de `vector`/`embedding` en el schema).

### 2.2 Modelo de datos

- `SourceFragment` — `id`, `sourceVersionId` (FK a la versión de `PROJECT_SOURCE`), `projectId` (denormalizado para aislamiento por proyecto, AGENTS.md §4.2/§37 — **obligatorio**, nunca joins implícitos para filtrar), `sequence`, `content` (texto del fragmento), `page`/`section`/`speaker`/`timestamp` (metadata opcional, spec §37), `embedding` (`Unsupported("vector(1536)")` o la dimensión que use el proveedor de embeddings elegido).
- Índice HNSW o IVFFlat sobre `embedding` (`CREATE INDEX ... USING hnsw (embedding vector_cosine_ops)`, en SQL de migración manual ya que Prisma no soporta índices vectoriales nativamente — patrón ya usado en este proyecto para la propia extensión `vector`).

### 2.3 Proveedor de embeddings

Nueva abstracción `EmbeddingProvider` en `packages/integrations/src/embedding-provider.ts`, mismo patrón que `DiagramProvider`/`MockupProvider`:
```
interface EmbeddingProvider {
  readonly id: string;
  embed(texts: string[]): Promise<number[][]>;
}
```
Implementación real detrás del mismo `AI_PROVIDER`/cadena de fallback ya configurada (reusar `packages/ai`, no crear una segunda abstracción de proveedor de IA — AGENTS.md §36.2). Un `DisabledEmbeddingProvider` debe existir para cuando no hay proveedor configurado (fallback manual, AGENTS.md §4.6/§56).

### 2.4 Backend

- Job asíncrono (worker BullMQ, reutilizando la cola ya existente en `apps/worker` o una nueva `KNOWLEDGE_BASE_EMBEDDING_QUEUE` en `packages/domain`) que, al aprobar una versión de `PROJECT_SOURCE`, fragmenta el texto extraído y genera embeddings — nunca de forma síncrona en el request HTTP (AGENTS.md §40).
- `KnowledgeBaseService.retrieve(projectId, query, strategy)` — implementa las 5 estrategias ya nombradas en AGENTS.md §37 (`NONE`, `ARTIFACT_ONLY`, `SOURCE_ONLY`, `HYBRID`, `FULL_PROJECT`). `HYBRID` combina full-text search de Postgres + similitud vectorial.
- Integrar la recuperación como contexto adicional en los prompts existentes de generación (Requirements, Use Cases, etc.) — **aditivo**, no reemplaza el flujo actual de "versión exacta de Contexto aprobada" como entrada principal.

### 2.5 Aislamiento (crítico)

Toda consulta de `SourceFragment` **debe** filtrar por `projectId` explícitamente en el `WHERE`, nunca confiar solo en el join — este es exactamente el caso P0 que AGENTS.md §37 señala ("Project A fragments/embeddings must never appear in Project B retrieval").

### 2.6 Pruebas mínimas requeridas

- Unit: fragmentación de texto, `KnowledgeBaseService.retrieve` con cada estrategia (usando un `FakeEmbeddingProvider`).
- Integration: aislamiento cross-project de fragmentos/embeddings (prueba explícita, con dos proyectos reales en la BD de test).

## 3. Incremento 3 — Impact Analysis

### 3.1 Motivación

Ya existe `StalenessService` (determinístico, sin IA, estados `CURRENT`/`NEWER_APPROVED_KNOWLEDGE_AVAILABLE`/`POTENTIALLY_AFFECTED`, propagado 2 saltos). Impact Analysis es la evolución: en vez de solo señalar "podría estar afectado", debe identificar **qué artefactos concretos** dependen de uno que cambió, usando el propio grafo de `TraceabilityService.buildGraph` ya existente (reutilizar, no duplicar — AGENTS.md §22 ya pide esto explícitamente: "When upstream artifacts change, Impact Analysis should identify affected implementation artifacts").

### 3.2 Diseño

**No requiere modelo Prisma nuevo** — es una consulta derivada sobre `TraceabilityService` + `StalenessService` ya existentes. Nuevo servicio `ImpactAnalysisService`:

```
analyzeChange(projectId, artifactVersionId): {
  directlyAffected: ArtifactRef[];   // 1 salto en el grafo de trazabilidad
  transitivelyAffected: ArtifactRef[]; // BFS completo aguas abajo, con profundidad
  recommendedReviewOrder: ArtifactRef[]; // orden topológico
}
```

Endpoint: `GET /projects/{projectId}/impact-analysis/{artifactVersionId}` (patrón de rutas ya establecido, AGENTS.md §33).

### 3.3 Frontend

Nueva vista o extensión de la página de Trazabilidad existente (`apps/web/app/traceability/page.tsx`, ya tiene vista de lista + grafo Mermaid con zoom/arrastre de la v1): al seleccionar un nodo, botón "Analizar impacto de un cambio aquí" que resalta en el grafo existente los nodos afectados (reutilizar `ZoomableDiagram`/`DiagramViewer` ya construidos, no crear un visor nuevo).

### 3.4 Pruebas mínimas requeridas

- Unit: BFS de propagación sobre grafos sintéticos (ciclos imposibles por diseño del grafo de trazabilidad, pero probar profundidad y ramificación).
- Integration: sobre el proyecto demo real, verificar que cambiar `CTX-001` marca como afectados los artefactos aguas abajo reales ya conocidos (RF-*, CU-*, etc., ver `docs/PRIMER_PARCIAL_FINAL_EVIDENCE.md` §14 para los datos reales de referencia).

## 4. Incremento 4 — Consistency Engine

### 4.1 Motivación

Verificación cruzada determinística entre artefactos, sin IA (AGENTS.md no la menciona como IA-dependiente, y el espíritu general del proyecto — "generic, structured, verifiable" — pide reglas determinísticas primero).

### 4.2 Diseño

Nuevo servicio `ConsistencyEngineService` con un conjunto de **reglas** (patrón idéntico a `RequirementQualityService`/`requirement-quality.ts` ya existente — reglas puras, deterministas, cada una produce `{rule, severity, message, affectedArtifactIds}`):

Reglas mínimas de v2 (extensible después, pero no especular más allá de esto ahora — YAGNI):
1. Todo Requisito `APPROVED` debe tener al menos un Caso de Uso que lo referencie (o quedar marcado como observación, no bloqueo — AGENTS.md nunca debe bloquear el flujo, solo advertir).
2. Toda pantalla del UI Blueprint debe tener al menos un Mockup asociado.
3. Todo nodo del árbol de Navegación debe corresponder a una pantalla del UI Blueprint (si existe UI Blueprint aprobado).
4. Ningún Caso de Uso `APPROVED` debe tener un nombre duplicado dentro del mismo proyecto (hallazgo real de la auditoría v1 — CU-002/CU-007 — es exactamente el tipo de cosa que esta regla debe señalar en el futuro).

Contrato de respuesta: reutilizar la forma ya establecida por `requirementQualityReportResponseSchema` (`standard`, `totalArtifacts`, `issues[]`) — mismo patrón, no inventar una forma nueva.

Endpoint: `GET /projects/{projectId}/consistency`.

### 4.3 Frontend

Sección nueva en la página de Readiness (`apps/web/app/readiness/page.tsx`, ya tiene la lista de 13 etapas) o una pestaña separada — mostrar issues agrupados por severidad, cada uno enlazando al artefacto afectado.

### 4.4 Pruebas mínimas requeridas

- Unit: cada regla, con casos positivos y negativos.
- Integration: correr sobre el proyecto demo real y confirmar el resultado esperado dado lo ya documentado en la auditoría (p. ej. debe señalar CU-002/CU-007 si la regla 4 está activa).

## 5. Incremento 5 — Baselines

### 5.1 Motivación

Ya existe versionado inmutable por artefacto individual (`ArtifactVersion`), pero no el concepto de "congelar el proyecto completo en un punto" — necesario para decir "esta es la versión oficial que se entregó/presentó".

### 5.2 Modelo de datos

- `ProjectBaseline` — `id`, `projectId`, `label` (ej. "Entrega Primer Parcial"), `createdAt`, `createdByUserId` (requiere Incremento 1), `description?`.
- `ProjectBaselineEntry` — `id`, `baselineId`, `artifactId`, `artifactVersionId` (la versión exacta congelada), único por `(baselineId, artifactId)`.

Un Baseline es **append-only**: una vez creado, nunca se edita (mismo principio que `ArtifactVersion`, AGENTS.md §31.3/§23 — "Do not silently overwrite a previous official snapshot").

### 5.3 Backend

`BaselinesService.create(projectId, label, description)` — toma automáticamente la versión `APPROVED` más reciente de cada artefacto (misma política de "versión autoritativa" ya centralizada en `FirstDeliverableSnapshotService`, reutilizar, no duplicar selección de versión — AGENTS.md §22/§4.4).

Endpoints: `POST /projects/{projectId}/baselines`, `GET /projects/{projectId}/baselines`, `GET /projects/{projectId}/baselines/{id}`.

`GET /projects/{projectId}/baselines/{id}/export` — reutiliza `renderExportHtml`/`ExportService` ya existentes, pero anclado a las versiones exactas del baseline en vez de "las más recientes aprobadas ahora mismo" (cambio pequeño: parametrizar `ExportService.buildSnapshot` para aceptar un mapa opcional de versiones fijas).

### 5.4 Frontend

Nueva página `apps/web/app/baselines/page.tsx`: crear baseline con nombre, listar baselines existentes, exportar un baseline específico (reutiliza el mismo flujo de descarga ya construido en `readiness/page.tsx`).

### 5.5 Pruebas mínimas requeridas

- Unit: selección de versión autoritativa al crear el baseline.
- Integration: crear un baseline, aprobar una nueva versión de un artefacto después, y confirmar que el export del baseline sigue mostrando la versión vieja congelada (esta es la prueba que demuestra el valor real de la feature).

## 6. Orden de trabajo dentro de la rama

```
feat/v2-foundation
  ├─ commit(s): Incremento 1 (Identity/RBAC) — el más invasivo, hazlo primero y completo
  ├─ commit(s): Incremento 2 (Knowledge Base/RAG)
  ├─ commit(s): Incremento 3 (Impact Analysis) — depende del grafo de Trazabilidad ya existente
  ├─ commit(s): Incremento 4 (Consistency Engine)
  └─ commit(s): Incremento 5 (Baselines) — depende de Identity para createdByUserId
```

No mezclar incrementos en el mismo commit. Cada incremento termina con la batería de verificación de §7 en verde antes de continuar al siguiente.

## 7. Batería de verificación obligatoria (al final de cada incremento, y otra vez al final de todo)

```
pnpm run typecheck
pnpm run lint
pnpm run format:check
pnpm run build
pnpm run test:coverage      # umbral global 70%, no bajarlo (AGENTS.md §46)
pnpm --filter @caseflow-ai/web run test
pnpm run db:test:prepare && pnpm run db:test:migrate && pnpm run test:integration
pnpm run test:e2e           # al menos una vez al final, incluyendo el nuevo Escenario C de auth
```

Además, específicamente para este plan:
- `git status --short` limpio antes de cada commit (sin archivos sueltos).
- Confirmar que **ninguna** migración reescribe o elimina datos históricos existentes (AGENTS.md §32 — política de "agregar → migrar/backfill → actualizar app → verificar → remover después", nunca al revés).
- Confirmar aislamiento por proyecto con una prueba explícita por cada feature nueva que toque datos scoped a proyecto (Identity, Knowledge Base) — es P0/blocker si falla (AGENTS.md §62).

## 8. Riesgos específicos de este plan

| Riesgo | Mitigación |
|---|---|
| Incremento 1 (Auth) rompe las ~212 pruebas de integración existentes que hoy no autentican nada | Dimensionar tiempo explícitamente para actualizar los helpers de `apps/api/test/integration/support/test-app.ts` una sola vez (crear un usuario+sesión de prueba reutilizable), no archivo por archivo |
| Embeddings (Incremento 2) requieren un proveedor de IA real configurado para probarse de verdad | Diseñar y probar primero contra un `FakeEmbeddingProvider`; la integración real con el proveedor configurado se verifica manualmente, no en CI (AGENTS.md §36.7/§44 — evaluación real de IA separada de CI determinista) |
| Backfill de membership sobre datos ya existentes en producción/demo | Ejecutar el script de backfill manualmente y verificar antes de considerar el incremento terminado — nunca asumir que corrió bien sin comprobarlo |
| Alcance total es grande para "una sola pasada" | Si en la práctica un incremento resulta mucho más grande de lo estimado aquí, está permitido pausar y entregar lo hecho hasta ahí como una v2 parcial — no forzar los 5 incrementos si la calidad se ve comprometida (AGENTS.md §64: "prefer correctness, integrity, clarity... over speculative sophistication") |

## 9. Reporte final esperado del agente que ejecute este plan

Al terminar (todos los incrementos o los que se hayan completado), el agente debe reportar, siguiendo el mismo formato ya usado en este proyecto (AGENTS.md §61):

- **Implementado:** qué incrementos se completaron íntegros.
- **Verificado:** resultado real de cada comando de §7, no hipotético.
- **No verificado:** qué no se pudo correr y por qué.
- **Notas:** riesgos de §8 que se materializaron, decisiones de diseño no cubiertas por este plan que tuvo que tomar, y cualquier incremento que quedó parcial.
